## Décisions à connaître avant de reprendre un item du backlog

- **`ayah_facts` est la seule source de vérité du plan quotidien** — aucun recalcul à la volée dans les écrans : un seul moteur (`AppState.ensureDayPlan()`) écrit les lignes du jour dans cette table, tout le reste (nombre de versets du jour, sourates à réviser, streak, fraîcheur) se **lit** depuis la table plutôt que d'être recalculé indépendamment ailleurs. Toute feature touchant plan/récap/check-in doit respecter ce principe — c'est justement la dette que la Phase 6 a corrigée (voir `docs/DOCUMENTATION_TECHNIQUE.md`).
- **Migration SQLite sans backfill (2026-08-30)** — au dernier changement de schéma (introduction d'`ayah_facts`), les anciennes tables ont été droppées sans backfill ligne-par-ligne, décision prise parce qu'aucun utilisateur réel n'existait encore en production. **Ne pas reproduire cette décision sans redemander confirmation** si un futur changement de schéma intervient alors que l'app a de vrais utilisateurs.
- **Profils élèves multi-utilisateurs retirés délibérément (2026-09-01)** — `StudentProfile`/`StudentService`/`StudentProfileBar` ont existé puis ont été supprimés en entier suite à un retour utilisateur explicite (app mono-utilisateur, fonctionnalité jamais utile en pratique) — pas un oubli ni un nettoyage silencieux. Ne pas les réintroduire sans un besoin confirmé.
- **`RevisionUnit`/`SourateSelection` ont deux notions d'identité distinctes** — `RevisionUnit.==` (égalité de valeur sur `sourate.id`+`verseStart`+`verseEnd`) coexiste avec un dédoublonnage par `label` (String d'affichage) dans `plan_screen.dart`, et avec une clé composite `String` manuelle dans `AppState._sameSelections`. Aucune divergence de comportement connue aujourd'hui, mais à réconcilier (probablement vers `==`/`hashCode` sur les deux modèles) si l'un de ces fichiers est retouché — voir item dette technique ci-dessous.
- **`ayah_facts` = journal, pas juste une table de stats (2026-09-01)** — retour TestFlight sur "sourate démarrée sans verset appris disparaît" : la cause réelle n'était pas un manque de persistance ponctuel mais une rupture de la sémantique `reach=0` (visé/proposé) → `reach=1` (atteint) déjà en place côté `revise`, jamais appliquée côté `learn`. Corrigé en généralisant cette sémantique (`startLearning` écrit `ayah_id=1, reach=0` ; `unlearnVerse` repasse `reach=0` au lieu de `DELETE`) plutôt qu'en ajoutant un correctif local. Règles détaillées dans `CLAUDE.md` § « Modèle de données central : `ayah_facts` » — à relire avant toute nouvelle feature touchant apprentissage/révision/fraîcheur, ce fichier est le point de connexion entre tous ces domaines.
- **Cases cochées de PlanScreen fusionnées dans `ayah_facts.reach` (2026-09-02)** — `AppState._checkedRakaas` (état en mémoire + `SharedPreferences`, Sprint 7) supprimé : `PlanScreen` écrit désormais directement `reach` pour la plage exacte de la rakaa cochée (`AppState.toggleTodayUnitReach`/`reachStatusFor`, une seule requête groupée en Dart plutôt qu'une requête par rakaa). Conséquence assumée : si la pénurie de matière fait apparaître la même plage de versets sur 2 rakaas (`RevisionEngine._padCyclically`), cocher l'une coche l'autre automatiquement — `reach` est une vérité par verset/jour, pas par rakaa.
- **`sqflite_common_ffi` en dépendance de prod, pas dev-only (2026-09-02)** — `main.dart` bascule `databaseFactory` vers l'implémentation FFI desktop derrière `Platform.isWindows` (jamais vrai sur iOS/Android), ajouté pour pouvoir tester l'app sur Windows en local (aucun device mobile disponible sur cette machine). Contrepartie assumée : Dart ne fait pas de tree-shaking sur une branche `if (Platform.isX)` (condition runtime, pas compile-time), donc le paquet est bel et bien compilé dans le binaire iOS/Android même s'il n'y est jamais exécuté — léger surcoût de taille de binaire mobile pour un besoin purement dev. Un vrai découplage demanderait des points d'entrée séparés (`main_desktop.dart` compilé via `--target`) — pas fait, jugé disproportionné pour l'usage actuel (tests ponctuels sur cette machine, pas un besoin produit).
- **Vue Coran unifiée derrière `ayah_start`/`ayah_end` (2026-09-02)** — même principe que « `ayah_facts` seule source de vérité » ci-dessus, appliqué à l'affichage du texte coranique : `VerseBottomSheet`/`VerseRow` (`lib/widgets/`) sont le seul mécanisme d'affichage d'une plage de versets (sourate + `ayahStart` + `ayahEnd`), utilisé par Plan du jour, Récap et Apprendre. Toute nouvelle feature qui affiche du texte coranique pour une plage de versets doit réutiliser ce couple plutôt que réimplémenter une boucle `VerseService.getVerse` — c'est exactement la dette que `SurahReaderScreen` (supprimé) et le chiffre arabe-indic redondant avec un badge (supprimé) représentaient. Voir `docs/DOCUMENTATION_TECHNIQUE.md` §8.6.
- **Deux `daysRemaining` distincts et volontairement non unifiés (2026-09-02)** — `AppState.cycleSummary` (affichage HomeScreen/RecapScreen) peut tomber à 0 ("objectif atteint") ; `RevisionEngine.selectDayUnits`/`DaySelection.daysRemaining` (moteur, via `AppState.dayUnits`/`buildTodaySession`) reste toujours ≥ 1 pour ne jamais diviser par zéro dans `dailyTarget`. Une revue de code a suggéré de les unifier (faire dériver `cycleSummary` de `DaySelection` telle quelle) — délibérément non fait : ça aurait supprimé le message "objectif atteint" en cas de cycle dépassé. Ne pas fusionner ces deux valeurs sans retrancher explicitement ce comportement d'abord.

## Backlog

**Axe "data model" (analyse 2026-09-01)** — les 4 items P1/P2 en tête de table découlent directement de la correction du bug "sourate qui disparaît" : `ayah_facts` (journal daté, `reach=0` visé → `reach=1` atteint, granularité verset) est déjà capable d'alimenter bien plus que ce qu'il alimente aujourd'hui — voir `CLAUDE.md` § « Modèle de données central ». Avant de les lancer, trancher lesquels entrent dans le prochain sprint (probablement pas les 4 d'un coup) plutôt que de les traiter à la volée.

Complète le streak actuel (nombre de jours consécutifs) par une vue de régularité sur la durée |
